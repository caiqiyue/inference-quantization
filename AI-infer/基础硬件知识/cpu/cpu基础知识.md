# 一、CPU 到底是什么？

先考虑一个简单的问题。

假设我们写了一段 C++ 代码：

```
int a = 10;
int b = 20;

int c = a + b;
```

你知道最终：

```
c = 30;
```

但是，你有没有想过：

**为什么 CPU 能知道 `+` 是什么意思？**

它并不认识 C++ 中的 `int`、变量名 `a` 或者 `b`。

CPU 真正理解的是一系列**机器指令（Machine Instructions）**。

例如：

```
LOAD
ADD
STORE
```

这些只是帮助理解的抽象指令名称，不是某一种 CPU 的完整真实汇编语法。

它们分别表示：

* `LOAD`：将数据加载到寄存器。
* `ADD`：执行加法。
* `STORE`：将结果保存到指定位置。

因此，一段高级语言程序最终需要经过编译，转换成目标 CPU 能够执行的机器指令。

```
C++ 源代码
    │
    ▼
编译器
    │
    ▼
机器指令
    │
    ▼
CPU 执行
    │
    ▼
计算结果
```

CPU 的核心作用，就是**按照指令集定义执行程序，包括算术计算、逻辑判断、内存访问和控制流程**。

但仅仅知道这个定义，还不足以理解 CPU。

接下来，我们拆开 CPU 内部的结构。

---

# 二、CPU、Core、Thread 到底是什么关系？

这是第一个特别容易混淆的知识点。

你在服务器上执行：

```
lscpu
```

可能会看到：

```
CPU(s):                 128
Thread(s) per core:     2
Core(s) per socket:     32
Socket(s):              2
```

这意味着什么？

我们逐个解释。

## 2.1 CPU Socket：物理处理器

Socket 指的是主板上的处理器插槽。

例如：

```
服务器主板
│
├── CPU Socket 0
│      └── 一颗 AMD EPYC
│
└── CPU Socket 1
       └── 一颗 AMD EPYC
```

如果服务器有两个 Socket，并且都安装了 CPU，那么就有两颗物理处理器。

每颗处理器内部又包含多个 Core。

## 2.2 CPU Core：真正执行指令的核心

Core（核心）是 CPU 中能够执行指令的硬件计算单元。

假设一颗 CPU 有四个 Core：

```
CPU
│
├── Core 0
├── Core 1
├── Core 2
└── Core 3
```

每个 Core 都能够执行自己的指令流。

因此，在理想情况下，可以让四个 Core 分别执行四份独立的计算任务。

例如：

```
Core 0 → 计算任务 A

Core 1 → 计算任务 B

Core 2 → 计算任务 C

Core 3 → 计算任务 D
```

这就是多核并行的基础。

但需要注意：

**Core 并不是一个单独的加法器。**

一个现代 CPU Core 内部通常包含：

* 指令获取和解码单元。
* 多种算术和逻辑执行单元。
* 寄存器及寄存器重命名相关资源。
* Load/Store 单元。
* 分支预测机制。
* 多级缓存中的部分结构。

所以一个 Core 不只是“一次执行一条加法”，而是能够管理和执行复杂的指令流。

## 2.3 Thread：线程究竟是什么？

这里需要区分两个概念。

**软件线程（Software Thread）**

由操作系统管理，是程序执行的一条逻辑路径。

例如，你使用 C++：

```
std::thread t1(task1);
std::thread t2(task2);
```

这会创建两个软件线程。

**硬件线程（Hardware Thread）**

是 CPU Core 提供的硬件执行上下文。

例如，一些 CPU Core 支持 SMT（Simultaneous Multithreading，同时多线程）。

一个 Core 可以暴露两个逻辑 CPU，让操作系统能够将两个软件线程同时安排在这个 Core 上执行。

示意：

```
物理 CPU
│
├── Core 0
│   ├── Hardware Thread 0
│   └── Hardware Thread 1
│
├── Core 1
│   ├── Hardware Thread 2
│   └── Hardware Thread 3
│
└── ...
```

### 一个很重要的误区

**一个 Core 支持两个硬件线程，不代表它拥有两套完整的计算硬件。**

两个硬件线程通常会共享这个 Core 中的部分执行资源、缓存等。

SMT 的主要意义是：当一个线程因为某些原因无法充分利用执行资源时，另一个线程有机会使用这些资源。

因此：

\\[ \\boxed{2\\text{ 个硬件线程}\\neq2\\text{ 倍计算性能}} \\]甚至在某些计算密集型任务中，两个线程可能因为争夺资源而影响彼此的性能。

### 联系你的服务器

你之前接触的双路 EPYC 9334 环境具有：

\\[ 2\\times32=64 \\]个物理 Core。

每个 Core 支持两个硬件线程，因此操作系统可以看到：

\\[ 64\\times2=128 \\]个逻辑 CPU。

所以，当你在 llama.cpp 中设置：

```
--threads 64
```

它表示让推理使用指定数量的工作线程，而不是强制 CPU 执行 64 条指令。

至于这些线程最终运行在哪些 Core 上，还受到操作系统调度、CPU 亲和性和 NUMA 等因素影响。

**到这里，你应该清楚：CPU、Core 和 Thread 是不同层次的概念。**

# 三、CPU Core 内部如何执行一次计算？

现在进入今天最重要的一部分。

我们使用一个具体例子：

\\[ 5+3=8 \\]你可能觉得这太简单了。

但如果能够弄清楚 CPU 如何完成这次加法，后面理解 SIMD、矩阵乘法和量化 Kernel 就会容易得多。

## 3.1 CPU 为什么需要寄存器？

先认识一个非常重要的硬件组件：

**Register（寄存器）。**

寄存器是处理器内部用于保存操作数、地址、中间结果或控制状态的高速存储资源。

你可以先把它理解为：

> CPU 执行计算时，能够直接使用的一组非常快速的内部存储位置。

假设两个数字原本位于 RAM（主内存）中：

```
RAM
│
├── A = 5
│
└── B = 3
```

CPU 要执行加法，需要使操作数能够被相应的执行单元访问。

一个简化的过程是：

```
RAM
│
├── A = 5 ──────┐
│               │
└── B = 3 ──────┤
                ▼
         CPU 寄存器
          R1 = 5
          R2 = 3
                │
                ▼
           加法执行单元
                │
                ▼
             R3 = 8
```

这里有一个值得记住的关键点：

**CPU 的算术执行单元通常主要通过寄存器操作数进行计算，而不是直接把 RAM 当作加法器的输入端。**

不过，在真实 CPU 中，内存读取会经过缓存、Load/Store 单元和其他硬件结构，并不是每次都直接访问 RAM。

此外，x86 等架构存在带内存操作数的算术指令，但硬件内部仍需要完成相应的数据读取。

## 3.2 ALU 是什么？

ALU：

**Arithmetic Logic Unit（算术逻辑单元）。**

它负责执行某些算术和逻辑操作，例如：

* 整数加法、减法。
* 位运算。
* 比较操作。

对于：

```
int c = a + b;
```

CPU 可以使用整数加法执行资源完成计算。

但如果你写的是：

```
float c = a + b;
```

情况就有所不同。

浮点数加法通常由浮点执行单元完成。

它可能涉及我们上一轮讨论的：

```
读取浮点操作数
      │
      ▼
比较指数
      │
      ▼
对阶
      │
      ▼
有效数字加减
      │
      ▼
规格化与舍入
      │
      ▼
写回结果
```

所以：

**整数加法和浮点加法虽然在 C++ 中都写成 `+`，但底层执行机制并不相同。**

这也解释了为什么你做量化时，需要特别关注 FP32、BF16、FP4 等不同数值格式。

# 四、一条 CPU 指令是怎么执行的？

经典的教学模型将指令执行划分为五个阶段：

1. Fetch：取指。
2. Decode：译码。
3. Execute：执行。
4. Memory：访存。
5. Write Back：写回。

我们用下面这段代码理解：

```
int c = a + b;
```

假设编译器生成了相应的加载、加法和存储操作。

### 第一步：Fetch——取指

CPU 从指令缓存或更下层存储中取得将要执行的机器指令。

例如：

```
LOAD R1, [A]
```

这里的含义是：

将地址 A 对应的数据加载到寄存器 R1。

### 第二步：Decode——译码

CPU 需要识别这条指令。

例如判断：

* 这是加载指令还是加法指令？
* 操作数在哪里？
* 需要使用哪些执行资源？

### 第三步：Execute——执行

假设现在要执行：

```
ADD R3, R1, R2
```

CPU 根据寄存器中的数据执行：

\\[ 5+3=8 \\]结果暂时保存在指定寄存器中。

### 第四步：Memory——访存

并不是所有指令都需要数据访存。

例如，纯寄存器加法不一定访问数据缓存。

但 Load 和 Store 指令通常涉及缓存或内存层级。

### 第五步：Write Back——写回

计算结果写入相应的架构状态或寄存器结果中。

如果程序需要把结果保存到内存，可能还需要执行 Store 指令。

这里需要特别强调：

**这五个阶段是用于理解 CPU 的简化模型，不意味着现代 x86 CPU 严格按照这五步逐条执行指令。**

现代 CPU 通常具备流水线、超标量、乱序执行等机制。

下面我们就理解这些机制为什么重要。

---

# 五、为什么 CPU 一个 Core 不只是一次计算一条指令？

这是理解现代 CPU 性能的关键。

假设程序需要执行：

```
a = b + c;
d = e + f;
g = h + i;
```

这三个加法没有数据依赖。

也就是说：

计算 `a` 不需要等待 `d` 或 `g`。

如果一个处理器只能依次执行：

```
计算 a
   ↓
计算 d
   ↓
计算 g
```

就可能浪费一些执行资源。

现代高性能 CPU 会尝试同时推进多条指令。

这里涉及三个概念。

## 5.1 流水线（Pipeline）

流水线的核心思想是：

**将一条指令的处理过程拆分为多个阶段，使不同指令的不同阶段能够重叠执行。**

例如：


| 时刻 | 指令 A | 指令 B | 指令 C |
| ---- | ------ | ------ | ------ |
| T1   | 取指   |        |        |
| T2   | 译码   | 取指   |        |
| T3   | 执行   | 译码   | 取指   |
| T4   | 写回   | 执行   | 译码   |

这是简化示意。

注意，流水线提高的主要是**单位时间内完成的指令数量（吞吐量）**，不一定能降低单条指令从开始到结束的延迟。

## 5.2 超标量（Superscalar）

超标量处理器能够在一个时钟周期中发射或执行多条合适的指令。

例如，一个 Core 内部可能拥有多组执行单元。

当指令之间没有相互依赖，而且资源允许时，就有机会并行执行部分操作。

## 5.3 乱序执行（Out-of-Order Execution）

假设有三条操作：

```
指令 A：从内存读取 X

指令 B：使用 X 计算结果

指令 C：计算 3 + 5
```

B 必须等待 A。

但是 C 与 A、B 都没有关系。

如果内存读取耗时较长，CPU 不一定傻傻等待。

它可以先执行 C，再等待 B 所需的数据到达。

这就是乱序执行的基本思想。

当然，最终程序可观察的执行结果仍然必须满足相应的架构语义。

### 为什么量化工程师需要知道这些？

因为它帮助你理解：

**CPU 的性能不仅取决于时钟频率，还取决于指令级并行、数据依赖、执行单元以及访存行为。**

例如：

```
sum += x[i] * w[i];
```

这里每次循环都会读取之前的 `sum`。

这种累加存在数据依赖链。

CPU 可能通过展开循环、多个独立累加器、SIMD 等方式提升吞吐量。

这也是为什么高性能矩阵乘法 Kernel 的代码通常比简单的三层 `for` 循环复杂得多。

# 六、CPU Cache 与 RAM：为什么不能每次都从内存读取？

现在假设有一个矩阵乘法：

\\[ Y=XW^T \\]其中：

\\[ X=[1,2,3,4] \\]\\[ W=[5,6,7,8] \\]计算：

\\[ Y=1\\times5+2\\times6+3\\times7+4\\times8 \\]结果：

\\[ Y=70 \\]为了完成计算，CPU 需要读取 X 和 W 的数据。

这些数据通常位于内存或 Cache 中。

## 6.1 CPU 为什么需要 Cache？

因为 CPU 的执行速度与 RAM 的访问速度存在明显差距。

寄存器非常接近执行单元。

RAM 的访问延迟则通常要高得多。

如果 CPU 每执行一次计算都必须等待数据从 RAM 返回，就会浪费大量执行能力。

因此，现代 CPU 通常采用多级缓存。

```
CPU Core
│
├── 寄存器
│
├── L1 Cache
│
├── L2 Cache
│
└── L3 Cache（可能由多个 Core 共享）
         │
         ▼
       RAM
```

不同 CPU 的缓存组织不同，这只是典型示意。

它们通常具有以下特点：


| 存储层级 | 容量 | 访问延迟         |
| -------- | ---- | ---------------- |
| 寄存器   | 极小 | 很低             |
| L1 Cache | 较小 | 很低             |
| L2 Cache | 中等 | 较低             |
| L3 Cache | 较大 | 较高             |
| RAM      | 很大 | 远高于片上 Cache |

这里不需要一开始记住所有硬件的具体延迟。

你只需要知道：

**越靠近执行单元的数据，通常越容易被快速访问。**

## 6.2 用一个具体例子理解 Cache

假设：

```
float x[4] = {1, 2, 3, 4};
```

每个 FP32 占用 4 字节。

因此数组总共：

\\[ 4\\times4=16\\text{ Bytes} \\]很多现代 CPU 使用 64 字节 Cache Line。

如果访问：

```
x[0]
```

在 Cache Miss 的情况下，CPU 通常会将包含该地址的整个 Cache Line 加载到缓存中，而不是只读取这一个 4 字节数字。

因此，后续访问：

```
x[1]
x[2]
x[3]
```

就可能命中缓存。

这就是**空间局部性（Spatial Locality）**。

如果程序反复访问同一个数据，也可能利用**时间局部性（Temporal Locality）**。

### 和矩阵乘法有什么关系？

高性能矩阵乘法会尽量复用已经加载到 Cache 或寄存器中的数据。

例如：

```
加载一块 X
      │
      ▼
加载一块 W
      │
      ▼
多次复用这些数据
      │
      ▼
完成一部分矩阵计算
```

而不是每执行一次乘法，都重新访问 RAM。

这就是矩阵乘法中常见的：

**Blocking / Tiling（分块计算）**。

它是 CPU 和 GPU 高性能矩阵计算都非常重要的优化思想。

# 七、CPU 多核并行如何帮助 llama.cpp 推理？

我们来看一个更接近真实工作的例子。

假设你需要计算：

\\[ Y=XW^T \\]其中：

\\[ X=[1,2,3,4] \\]\\[ W= \\begin{bmatrix} 1&2&3&4\\\\ 2&3&4&5\\\\ 3&4&5&6\\\\ 4&5&6&7 \\end{bmatrix} \\]为了方便理解，这里把 W 的每一行看成一个输出通道的权重。

所以：

\\[ Y= \\begin{bmatrix} 30&40&50&60 \\end{bmatrix} \\]我们手算第一项：

\\[ Y\_0=1\\times1+2\\times2+3\\times3+4\\times4 \\]\\[ =1+4+9+16=30 \\]第二项：

\\[ Y\_1=1\\times2+2\\times3+3\\times4+4\\times5 \\]\\[ =2+6+12+20=40 \\]其余同理。

## 7.1 单线程执行

一种简单实现是：

```
for (int row = 0; row < 4; row++) {
    float sum = 0;

    for (int col = 0; col < 4; col++) {
        sum += X[col] * W[row][col];
    }

    Y[row] = sum;
}
```

每次处理 W 的一行。

## 7.2 四个线程并行

由于不同输出行之间没有数据依赖，可以把四行分配给四个工作线程。

```
Thread 0 → W 第 0 行 → Y[0] = 30

Thread 1 → W 第 1 行 → Y[1] = 40

Thread 2 → W 第 2 行 → Y[2] = 50

Thread 3 → W 第 3 行 → Y[3] = 60
```

假设它们被安排在四个不同的物理 Core 上，就可以真正并行执行。

当然，对于这种极小规模矩阵，创建和调度线程的成本可能远高于计算本身。

但当矩阵规模变大时，多核并行就可能带来明显的性能收益。

### 这里有三个不同层次的并行

你需要把它们分清楚：

**线程级并行：**

多个 CPU Core 分别执行不同的计算任务。

**指令级并行：**

同一个 Core 尝试重叠执行多条互不依赖的指令。

**数据级并行：**

通过 SIMD，让一条向量指令同时处理多个数据元素。

这三种并行机制可以相互配合，而不是互相替代。

SIMD 是我们下一节要重点学习的内容。

# 八、把前面的知识真正联系到 llama.cpp 量化

到这里，我们已经认识了：

* CPU Core。
* 软件线程和硬件线程。
* 寄存器。
* 整数与浮点执行单元。
* 指令执行。
* Cache。
* 多核并行。

现在看看它们在 NVFP4 量化中如何发挥作用。

假设你有一个已经量化的权重：

```
原始 BF16 权重
      │
      ▼
NVFP4 量化
      │
      ▼
FP4 编码 + Block Scale
      │
      ▼
打包存储在内存中
```

当 llama.cpp 在 CPU 上使用这些权重时，某种可能的计算实现是：

```
RAM 中的 NVFP4 数据
         │
         ▼
      CPU Cache
         │
         ▼
CPU 读取打包的 FP4 数据
         │
         ▼
解包 FP4 编码
         │
         ▼
根据 Scale 恢复数值
         │
         ▼
与激活值执行乘法
         │
         ▼
累加到输出结果
         │
         ▼
写回输出 Tensor
```

需要特别强调：

**这是帮助理解的概念流程，不代表你们 llama.cpp NVFP4 CPU Kernel 必须先将所有 FP4 权重完整反量化成 FP32，再执行矩阵乘法。**

真实实现完全可以在小循环内部融合解包、缩放、乘法与累加。

### 对应到硬件知识


| 操作                  | 对应 CPU 硬件或机制       |
| --------------------- | ------------------------- |
| 从内存读取 NVFP4 数据 | Load/Store 单元、Cache    |
| 解包两个 4-bit 数值   | 整数/位运算指令           |
| FP4 数值转换          | 标量或向量数值处理        |
| Scale 恢复            | 浮点运算                  |
| 矩阵乘法              | 浮点执行单元、SIMD        |
| 多行并行计算          | 多线程、多 Core           |
| 保存计算结果          | 寄存器、Store、Cache/内存 |

这张表非常重要。

以后你看到 llama.cpp 中的某段 C++ 量化代码，就能够逐渐将软件操作和硬件行为联系起来。

例如：

```
uint8_t packed = data[i];
```

这代表读取一个字节。

如果这个字节包含两个 FP4 编码：

```
uint8_t low  = packed & 0x0F;
uint8_t high = packed >> 4;
```

那么这里涉及的是整数位运算。

接下来根据编码恢复浮点数时，才进入数值转换和浮点计算过程。

**不要把 FP4 存储、FP4 解码和 FP4 乘法当成同一个硬件操作。**

# 九、CPU 推理为什么也存在性能瓶颈？

你以后做 Benchmark 时，会经常遇到一个问题：

增加线程数后，为什么推理速度没有线性提高？

例如：

```
8 Threads   → 20 tokens/s

16 Threads  → 32 tokens/s

32 Threads  → 40 tokens/s

64 Threads  → 43 tokens/s
```

这是一组假设数据，仅用于解释问题。

你可能会觉得：

线程数量翻倍，理论上性能不应该也翻倍吗？

其实不一定。

原因可能有很多：

### 1. 内存带宽有限

当多个 Core 同时读取大量权重时，所有核心需要竞争有限的内存带宽。

如果 RAM 已经无法提供更多数据，继续增加线程也不能让数据传输变快。

### 2. Cache 容量有限

多个线程处理的数据可能无法全部保存在 Cache 中。

Cache Miss 增加，CPU 需要频繁访问 RAM。

### 3. 多线程调度成本

线程同步、任务划分和调度都需要额外开销。

尤其对于较小的矩阵计算，线程开销可能抵消并行收益。

### 4. SMT 资源竞争

如果 64 个物理 Core 已经充分使用其执行资源，再增加 SMT 线程不一定带来明显收益。

### 5. NUMA

这一点与你的双路 CPU 服务器有关。

NUMA 全称：

**Non-Uniform Memory Access（非统一内存访问）**。

简单说，在多路服务器中，不同 CPU Socket 访问不同内存区域的成本可能不同。

例如：

```
Socket 0 ── 本地 RAM 0
    │
    │ CPU 间互连
    │
Socket 1 ── 本地 RAM 1
```

Socket 0 访问本地 RAM，通常比通过互连访问 Socket 1 所连接的 RAM 更有优势。

所以在双路服务器上，线程与内存的分布也可能影响 llama.cpp 的 CPU 推理性能。

NUMA 的详细优化可以等学习完内存带宽后再深入，目前知道它是什么即可。

# 十、今天的知识总结

把整节课压缩成一张表：


| 概念            | 你应该记住什么                           |
| --------------- | ---------------------------------------- |
| CPU             | 执行程序指令的通用处理器                 |
| Core            | 执行指令的物理计算核心                   |
| Software Thread | 操作系统调度的程序执行线程               |
| Hardware Thread | CPU 提供的硬件执行上下文                 |
| Register        | 执行计算时使用的高速内部存储             |
| ALU             | 负责整数算术和逻辑运算的硬件单元         |
| 浮点执行单元    | 执行浮点运算的硬件资源                   |
| Pipeline        | 重叠不同指令的执行阶段                   |
| 乱序执行        | 在满足依赖和架构语义的情况下调整执行次序 |
| CPU Cache       | 缓解 CPU 与 RAM 之间的访问速度差距       |
| 多核并行        | 将独立计算任务分配给不同 Core            |
| NUMA            | 不同处理器核心访问内存的成本可能不同     |

你可以建立一个整体认知：

```
llama.cpp 程序
       │
       ▼
操作系统调度工作线程
       │
       ▼
CPU Core 执行机器指令
       │
       ├── 寄存器保存操作数
       │
       ├── ALU / 浮点单元执行计算
       │
       ├── Cache 提供数据
       │
       └── Load/Store 单元访问内存
       │
       ▼
完成矩阵乘法或量化计算
```
