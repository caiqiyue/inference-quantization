# 1. 先建立总框架：大模型推理到底在做什么

从底层看，大模型推理并不神秘。

它可以粗略拆成三件事：

\[
\boxed{
\text{LLM 推理}
=
\text{数据搬运}
+
\text{矩阵计算}
+
\text{其他算子}
}
\]

其中，大头通常是：

- 读取模型权重
- 读取 activation
- 做矩阵乘法
- 做 Attention、Softmax、Norm 等计算
- 保存中间结果
- 继续进入下一层

一个典型 Transformer Layer 中，会不断出现：

\[
Q=XW_Q
\]

\[
K=XW_K
\]

\[
V=XW_V
\]

以及 MLP：

\[
Y=XW_1
\]

\[
Z=YW_2
\]

也就是说：

> **大模型推理的核心工作之一，就是不断把权重搬到计算单元附近，再执行大量乘法和累加。**

---

# 2. 计算机里最重要的两件事：搬数据和做计算

你可以把计算机简化成：

```text
存数据的地方
    ↓
搬数据的通道
    ↓
真正做计算的硬件
```

例如 GPU 推理：

```text
SSD
 ↓
RAM
 ↓ PCIe
VRAM
 ↓
Cache
 ↓
Register
 ↓
CUDA Core / Tensor Core
```

CPU 推理：

```text
SSD
 ↓
RAM
 ↓
L3 Cache
 ↓
L2 Cache
 ↓
L1 Cache
 ↓
Register
 ↓
ALU / FPU / SIMD
```

所以：

> **计算不是“数据放在内存里，CPU/GPU 直接远程算”。**

真正计算前，数据必须逐渐搬到离计算单元越来越近的位置。

# 3. CPU 的基本结构和计算路径

CPU 可以理解成：

> **少量、很强、很灵活的计算核心。**

一个极度简化的 CPU：

```text
CPU
│
├── Core 0
│   ├── Register
│   ├── L1 Cache
│   ├── ALU
│   ├── FPU
│   └── SIMD Unit
│
├── Core 1
├── Core 2
├── ...
│
├── L2 Cache
├── L3 Cache
│
└── Memory Controller
         │
         ↓
        RAM
```

## 3.1 ALU

Arithmetic Logic Unit。

主要处理：

- 整数加减
- 位运算
- 逻辑判断

---

## 3.2 FPU

Floating Point Unit。

主要用于：

- FP32
- FP64
- 浮点加减乘除

现代 CPU 的真实设计会更复杂，但作为理解量化的基础，这样理解已经足够。

---

## 3.3 Register

Register，即寄存器。

可以理解为：

> **CPU 工人手里正在拿的数据。**

特点：

- 极快
- 极小
- 离执行单元最近

---

## 3.4 Cache

Cache 是 CPU 附近的高速缓存。

一般有：

```text
L1
L2
L3
```

总体规律：

```text
越靠近 CPU：
速度越快
容量越小
成本越高
```

可以类比：

```text
Register = 手里
L1       = 桌面
L2       = 抽屉
L3       = 房间里的柜子
RAM      = 楼下仓库
SSD      = 城外仓库
```

# 4. GPU 的基本结构和计算路径

GPU 的设计目标和 CPU 不一样。

CPU 更像：

> 少量非常聪明、单兵能力很强的人。

GPU 更像：

> 数量巨大的计算工人，同时处理大量类似任务。

极度简化的 GPU：

```text
GPU
│
├── SM 0
│   ├── CUDA Core
│   ├── Tensor Core
│   ├── Registers
│   ├── Shared Memory
│   └── L1 Cache
│
├── SM 1
├── SM 2
├── ...
│
├── L2 Cache
│
├── Memory Controller
│
└── VRAM
```

---

## 4.1 SM

NVIDIA GPU 中常见：

\[
SM = Streaming\ Multiprocessor
\]

可以把每个 SM 理解成一个“小型并行计算工厂”。

其中有：

- CUDA Core
- Tensor Core
- Register
- Shared Memory
- L1 Cache

GPU 由很多个 SM 组成。

# 5. RAM、VRAM、Cache、Register 到底是什么

这一部分是理解大模型推理的核心。

## 5.1 RAM

RAM 是 CPU 主要使用的大容量内存。

例如：

```text
32 GB DDR4
64 GB DDR5
```

模型运行时，模型文件一般会先从 SSD 加载进 RAM。

---

## 5.2 VRAM

VRAM 是 GPU 自己的显存。

例如：

```text
RTX 4070 Ti SUPER
16 GB VRAM
```

如果模型放进 GPU 推理，一般流程是：

```text
SSD
 ↓
RAM
 ↓ PCIe
VRAM
```

之后 GPU 的主要计算围绕：

```text
VRAM ↔ GPU Core
```

进行。

正常情况下，并不是每算一层都重新从 RAM 通过 PCIe 把权重传一遍。

---

## 5.3 Cache

Cache 是更靠近计算单元的小型高速存储。

CPU：

```text
RAM
 ↓
L3
 ↓
L2
 ↓
L1
```

GPU：

```text
VRAM
 ↓
L2
 ↓
L1 / Shared Memory
```

---

## 5.4 Register

真正计算前，数据最终通常需要进入寄存器。

因此可以记住：

```text
内存 / 显存
   ↓
Cache
   ↓
Register
   ↓
计算单元
```

# 6. 什么是内存带宽，和总线是什么关系

## 6.1 容量和带宽不是一回事

例如：

```text
显存容量：16 GB
显存带宽：500 GB/s
```

容量表示：

> 仓库能放多少东西。

带宽表示：

> 每秒最多能搬多少东西。

---

## 6.2 总线和带宽

可以类比高速公路：

- 总线：道路
- 总线宽度：有多少条车道
- 频率：车辆通过速度
- 带宽：这条路单位时间总共能运多少货

简化来看：

\[
\boxed{
Bandwidth \approx Bus\ Width \times Transfer\ Rate
}
\]

例如：

```text
总线宽
+
传输频率高
```

就意味着更高的数据传输能力。

---

## 6.3 PCIe 带宽和显存带宽不是一回事

第一条路径：

```text
CPU RAM
 ↓
PCIe
 ↓
GPU VRAM
```

这是 PCIe 带宽。

第二条路径：

```text
GPU VRAM
 ↓
GPU Core
```

这是显存带宽。

对正常 GPU 推理来说，模型完全装进显存之后，持续影响 decode 性能的通常是：

\[
\boxed{\text{VRAM 带宽}}
\]

---

# 7. SIMD、SIMT、CUDA Core、Tensor Core

## 7.1 CPU：SIMD

SIMD：

\[
Single\ Instruction,\ Multiple\ Data
\]

意思是：

> 一条指令，同时处理多个数据。

例如 AVX2 是 256-bit 向量宽度。

FP32 每个 32 bit：

\[
256 / 32 = 8
\]

所以一个 256-bit 向量寄存器理论上可以装：

\[
8\ 个 FP32
\]

如果 INT8：

\[
256 / 8 = 32
\]

理论上可以装：

\[
32\ 个 INT8
\]

常见 CPU SIMD：

- SSE
- AVX
- AVX2
- AVX-512
- ARM NEON

这也是 llama.cpp CPU 推理非常关注指令集优化的原因。

---

## 7.2 GPU：SIMT

GPU 更常讲：

\[
SIMT = Single\ Instruction,\ Multiple\ Threads
\]

例如 NVIDIA 一个 warp 通常：

\[
32\ threads
\]

可以理解成：

```text
thread 0 处理 data[0]
thread 1 处理 data[1]
...
thread31 处理 data[31]
```

很多线程成组执行相同或相似的指令。

---

## 7.3 CUDA Core

CUDA Core 可以粗略理解成：

> GPU 中普通的计算单元。

可以做：

- 浮点计算
- 整数计算
- 加减乘
- 一般逻辑运算

---

## 7.4 Tensor Core

Tensor Core 是专门针对矩阵乘加设计的硬件。

典型目标：

\[
D=A\times B+C
\]

神经网络中的：

- Linear
- Attention
- MLP

都大量依赖矩阵计算。

Tensor Core 通常对：

- FP16
- BF16
- TF32
- FP8
- INT8

等低精度格式具有较高吞吐。

---

# 8. 用一个小例子完整跑一遍 CPU 矩阵乘法

计算：

\[
y=xW
\]

其中：

\[
x=
\begin{bmatrix}
1&2&3&4
\end{bmatrix}
\]

\[
W=
\begin{bmatrix}
1&2\\
3&4\\
5&6\\
7&8
\end{bmatrix}
\]

因此：

\[
y_0=1\times1+2\times3+3\times5+4\times7
\]

\[
=1+6+15+28=50
\]

\[
y_1=1\times2+2\times4+3\times6+4\times8
\]

\[
=2+8+18+32=60
\]

最终：

\[
\boxed{
y=[50,60]
}
\]

---

## 8.1 模型最初在 SSD

假设 W 是 FP32。

每个 FP32：

\[
32bit=4Byte
\]

W 有 8 个数：

\[
8\times4=32Byte
\]

x 有 4 个数：

\[
4\times4=16Byte
\]

---

## 8.2 SSD → RAM

程序启动后：

```text
model.gguf / model weights
        ↓
       SSD
        ↓
      RAM
```

可以假设 RAM 中：

```text
0x1000    1.0
0x1004    2.0
0x1008    3.0
...
```

---

## 8.3 RAM → Cache

CPU 想访问 W[0]。

它会先检查：

```text
L1 有吗？
 ↓
L2 有吗？
 ↓
L3 有吗？
 ↓
RAM
```

如果前面都没有，就发生：

\[
\boxed{Cache\ Miss}
\]

然后从 RAM 读取数据。

---

## 8.4 Cache Line

CPU 通常不是只读一个 4 Byte 的 FP32。

现代 CPU 常见 cache line：

\[
64Byte
\]

也就是说，即使 CPU 只想读：

```text
W[0]
```

它可能把附近一整块 64 Byte 一起拉进 Cache。

我们的 W 只有：

\[
32Byte
\]

所以可能一次就把整个 W 带入 Cache。

---

## 8.5 Cache → Register

接下来 CPU 把真正需要计算的数据加载到寄存器。

标量方式：

```text
R1 = x[0] = 1
R2 = W[0,0] = 1
ACC = 0
```

执行：

\[
ACC=ACC+R1\times R2
\]

得到：

\[
ACC=1
\]

继续：

```text
2 × 3
3 × 5
4 × 7
```

得到：

\[
50
\]

---

## 8.6 FMA

现代 CPU 经常使用：

\[
FMA = Fused\ Multiply\ Add
\]

即：

\[
ACC = ACC + a\times b
\]

这是矩阵乘法最核心的操作之一。

---

## 8.7 SIMD 版本

假设使用 128-bit SIMD。

FP32 每个 32bit：

\[
128/32=4
\]

于是：

```text
Xreg = [1,2,3,4]
Wreg = [1,3,5,7]
```

一次向量乘：

```text
[1,2,3,4]
×
[1,3,5,7]
=
[1,6,15,28]
```

再求和：

\[
1+6+15+28=50
\]

这就是 CPU 高性能矩阵计算的基本思想：

> **一次搬一批，一次算一批。**

# 10. 为什么大模型推理经常不是算得慢，而是搬得慢

现代 GPU 的计算能力极强。

假设一块 GPU：

```text
理论计算能力非常高
```

但显存带宽有限。

如果一个 7B 模型使用 FP16：

\[
7\times10^9\times2Byte
\approx14GB
\]

生成一个 token 时，需要访问大量模型权重。

于是 GPU 可能出现：

```text
计算单元：
我已经算完上一批了。

数据呢？

……

还在从 VRAM 搬。

……

到了。

啪，算完。

下一批呢？
```

这就是：

\[
\boxed{Memory\ Bound}
\]

---

# 11. Memory Bound 和 Compute Bound

## 11.1 Memory Bound

如果：

\[
T_{memory} \gg T_{compute}
\]

说明主要时间花在：

> 搬数据。

这叫：

\[
\boxed{Memory\ Bound}
\]

---

## 11.2 Compute Bound

如果：

\[
T_{compute} \gg T_{memory}
\]

说明主要时间花在：

> 真正执行乘法、加法等计算。

这叫：

\[
\boxed{Compute\ Bound}
\]

---

## 11.3 Arithmetic Intensity

定义：

\[
AI=
\frac{\text{计算量}}
{\text{内存访问量}}
\]

例如：

\[
AI=
\frac{FLOPs}{Bytes}
\]

如果：

```text
搬很多数据
只算很少
```

AI 低，更容易 Memory Bound。

如果：

```text
搬一点数据
反复做很多计算
```

AI 高，更容易 Compute Bound。

# 12. Prefill 和 Decode 为什么性能特点不同

LLM 推理主要分：

```text
Prefill
+
Decode
```

---

## 12.1 Prefill

输入：

```text
“请解释什么是量化”
```

假设有 100 个 token。

Prefill 可以一次处理很多 token：

\[
[100,4096]\times[4096,4096]
\]

一块权重读进来，可以同时服务很多 token。

因此：

- 权重复用率高
- Arithmetic Intensity 高
- 更容易 Compute Bound

---

## 12.2 Decode

生成时：

```text
量
↓
化
↓
是
↓
...
```

一次只生成一个 token。

这时：

\[
[1,4096]\times[4096,4096]
\]

需要搬很大的 W，却只服务一个 token。

因此：

- 权重复用率低
- Arithmetic Intensity 低
- 更容易 Memory Bound

所以：

> **小 batch 自回归 decode 是权重量化特别容易产生收益的场景。**

# 12A. 计算密度（Arithmetic Intensity）与 Roofline Model

这一部分是理解“为什么有些量化特别有效、有些量化收益却有限”的核心。

## 12A.1 什么是计算密度

计算密度更标准的英文名称是：

\[
\boxed{\text{Arithmetic Intensity}}
\]

常缩写为：

\[
AI
\]

它描述的是：

> **每搬运 1 Byte 数据，能够完成多少次计算。**

定义：

\[
\boxed{
AI=\frac{\text{计算量}}{\text{数据搬运量}}
}
\]

常见单位：

\[
\text{FLOPs/Byte}
\]

例如，一个算子：

- 一共搬运 \(100\text{ Byte}\)
- 一共执行 \(200\text{ FLOPs}\)

那么：

\[
AI=\frac{200}{100}=2\text{ FLOPs/Byte}
\]

意思就是：

> 每搬 1 Byte 数据，只做 2 次浮点运算。

这种算子的计算密度比较低。

---

## 12A.2 为什么计算密度能决定瓶颈

一块 CPU/GPU 可以粗略看成有两个极限：

1. **Peak Compute**：每秒最多能做多少计算。
2. **Memory Bandwidth**：每秒最多能搬多少数据。

假设一块 GPU：

\[
\text{Peak Compute}=100\text{ TFLOPS}
\]

显存带宽：

\[
\text{Memory Bandwidth}=1\text{ TB/s}
\]

如果某个算子的计算密度：

\[
AI=2\text{ FLOPs/Byte}
\]

那么显存每秒能够提供的数据，最多支撑：

\[
1\text{ TB/s}\times2\text{ FLOPs/Byte}
\]

约等于：

\[
2\text{ TFLOPS}
\]

虽然 GPU 理论上可以达到：

\[
100\text{ TFLOPS}
\]

但因为数据供应速度只能支持大约：

\[
2\text{ TFLOPS}
\]

所以真正限制性能的是数据搬运。

这就是：

\[
\boxed{\text{Memory Bound}}
\]

可以理解成：

```text
GPU 计算能力：100
内存只能喂给它够算 2 的数据

结果：
大量计算单元在等待数据
```

---

## 12A.3 Compute Bound 的情况

如果：

\[
AI=200\text{ FLOPs/Byte}
\]

那么按照内存带宽：

\[
1\text{ TB/s}\times200\text{ FLOPs/Byte}
=
200\text{ TFLOPS}
\]

也就是说，内存理论上可以提供足够支撑 \(200\text{ TFLOPS}\) 的数据。

但是 GPU 自己只有：

\[
100\text{ TFLOPS}
\]

因此瓶颈变成：

> GPU 本身已经算不过来了。

这就是：

\[
\boxed{\text{Compute Bound}}
\]

---

## 12A.4 Roofline Model 的核心公式

Roofline Model 可以用一个非常重要的公式来概括：

\[
\boxed{
P_{\text{actual}}
\approx
\min
\left(
P_{\text{peak}},
BW\times AI
\right)
}
\]

其中：

- \(P_{\text{actual}}\)：实际可达到的计算性能
- \(P_{\text{peak}}\)：硬件峰值计算性能
- \(BW\)：内存带宽
- \(AI\)：Arithmetic Intensity

也就是说：

> 实际性能同时受到“计算能力”和“数据供应能力”限制，哪个先到极限，哪个就是瓶颈。

---

## 12A.5 Memory Bound 和 Compute Bound 的分界点

分界点可以由：

\[
BW\times AI=P_{\text{peak}}
\]

得到：

\[
\boxed{
AI_{\text{critical}}
=
\frac{P_{\text{peak}}}{BW}
}
\]

还是前面的例子：

\[
P_{\text{peak}}=100\text{ TFLOPS}
\]

\[
BW=1\text{ TB/s}
\]

那么：

\[
AI_{\text{critical}}
=
\frac{100}{1}
=
100\text{ FLOPs/Byte}
\]

因此可以粗略判断：

\[
AI<100
\]

更偏：

\[
\boxed{\text{Memory Bound}}
\]

而：

\[
AI>100
\]

更偏：

\[
\boxed{\text{Compute Bound}}
\]

注意：

> 这个临界值不是固定常数，它取决于具体 CPU/GPU、具体精度、具体 Kernel、具体内存层级。

---

## 12A.6 为什么 LLM Decode 的计算密度通常很低

考虑一个 Linear：

\[
x\in\mathbb{R}^{1\times4096}
\]

\[
W\in\mathbb{R}^{4096\times4096}
\]

权重数量：

\[
4096\times4096
=
16{,}777{,}216
\]

约：

\[
16.8\text{ M}
\]

一次矩阵向量乘法中，每个权重大致参与：

- 1 次乘法
- 1 次加法

所以可以粗略按照：

\[
2\text{ FLOPs/weight}
\]

估算总计算量：

\[
16.8\text{ M}\times2
\approx
33.6\text{ MFLOPs}
\]

如果权重使用 FP16：

\[
2\text{ Byte/weight}
\]

那么权重本身的数据量约为：

\[
16.8\text{ M}\times2
\approx
33.6\text{ MB}
\]

忽略相对较小的输入和输出数据：

\[
AI
\approx
\frac{33.6\text{ MFLOPs}}
{33.6\text{ MB}}
\]

因此：

\[
\boxed{
AI\approx1\text{ FLOP/Byte}
}
\]

这个值非常低。

原因是：

> Decode 时只有一个 token，却要读取整个巨大的权重矩阵。

也就是：

```text
搬大量 Weight
↓
每个 Weight 基本只服务当前一个 token
↓
数据复用率低
↓
Arithmetic Intensity 低
↓
更容易 Memory Bound
```

---

## 12A.7 为什么 Prefill 的计算密度更高

如果输入不是一个 token，而是 100 个 token：

\[
X\in\mathbb{R}^{100\times4096}
\]

仍然乘：

\[
W\in\mathbb{R}^{4096\times4096}
\]

同一个权重矩阵 \(W\) 可以被 100 个 token 重复使用。

也就是：

```text
搬一次 W
↓
给 token 1 使用
给 token 2 使用
给 token 3 使用
...
给 token 100 使用
```

于是：

- 权重搬运量没有增加 100 倍
- 计算量却大幅增加

所以：

\[
AI\uparrow
\]

Prefill 因此通常比单 token Decode 更接近：

\[
\boxed{\text{Compute Bound}}
\]

---

## 12A.8 量化如何改变计算密度

还是前面的 Decode Linear。

FP16 权重：

\[
33.6\text{ MB}
\]

计算量：

\[
33.6\text{ MFLOPs}
\]

因此：

\[
AI_{\text{FP16}}
\approx
1\text{ FLOP/Byte}
\]

如果把权重量化成 INT4：

\[
0.5\text{ Byte/weight}
\]

权重大小变成：

\[
16.8\text{ M}\times0.5
=
8.4\text{ MB}
\]

而原本要完成的矩阵乘法任务没有发生数量级变化：

\[
\approx33.6\text{ MFLOPs}
\]

于是：

\[
AI_{\text{INT4}}
\approx
\frac{33.6}{8.4}
=
4\text{ FLOPs/Byte}
\]

因此：

\[
\boxed{
AI:1\rightarrow4\text{ FLOPs/Byte}
}
\]

本质上不是“数学计算突然变多了”，而是：

\[
\boxed{
\text{Bytes Moved}\downarrow
}
\]

于是：

\[
\boxed{
\frac{\text{Operations}}{\text{Bytes Moved}}
\uparrow
}
\]

也就是说：

> 同样搬 1 Byte 数据，现在可以支撑更多有效计算。

---

## 12A.9 为什么量化特别适合 Memory Bound 场景

如果一个算子已经是：

\[
\boxed{\text{Memory Bound}}
\]

说明它当前的问题是：

> 算力还有富余，但数据送不过来。

此时即使把计算单元速度提高两倍，收益也可能有限。

因为：

```text
计算单元：
我还能算更多。

Memory：
但是我没法更快给你数据。
```

而量化：

```text
FP16
↓
INT8 / INT4
```

直接减少：

\[
\text{Bytes Moved}
\]

因此显著缓解内存带宽压力。

所以通常：

\[
\boxed{
\text{Memory Bound}
\Rightarrow
\text{量化的带宽收益特别重要}
}
\]

---

## 12A.10 如果本来是 Compute Bound 呢

如果某个大矩阵 GEMM 已经：

```text
数据供应充足
Tensor Core 接近满负荷
```

那么瓶颈是：

\[
\boxed{\text{Compute Bound}}
\]

此时单纯让权重文件更小，未必能带来很大的计算性能提升。

真正重要的是：

> 低精度是否让硬件的实际计算吞吐提高。

例如：

```text
FP16 Tensor Core
↓
FP8 Tensor Core
```

如果 FP8 路径的峰值计算吞吐更高，那么：

\[
P_{\text{peak}}\uparrow
\]

这才会直接改善 Compute Bound 算子。

因此：

\[
\boxed{
\text{Compute Bound}
\Rightarrow
\text{更关注低精度计算吞吐}
}
\]

---

## 12A.11 用 Roofline 图建立直觉

可以把 Roofline Model 想成：

```text
性能
 ^
 |                         ───────────── Peak Compute
 |                       /
 |                     /
 |                   /
 |                 /
 |               /
 |             /
 |           /
 |         /
 |_______/________________________________> Arithmetic Intensity
        ↑
      分界点
```

左半边：

\[
\boxed{\text{Memory Bound}}
\]

性能主要由：

\[
BW\times AI
\]

决定。

右半边：

\[
\boxed{\text{Compute Bound}}
\]

性能主要由：

\[
P_{\text{peak}}
\]

决定。

两者交点：

\[
\boxed{
AI_{\text{critical}}
=
\frac{P_{\text{peak}}}{BW}
}
\]

---

## 12A.12 对量化最实用的判断方法

以后分析一个算子是否适合量化加速，可以先问两个问题。

### 问题 1：一份数据搬进来后，会被重复利用多少次？

如果：

```text
搬一次
↓
只算一次
```

通常：

\[
AI\低
\]

容易：

\[
\boxed{\text{Memory Bound}}
\]

如果：

```text
搬一次
↓
重复参与很多次计算
```

通常：

\[
AI\高
\]

更容易：

\[
\boxed{\text{Compute Bound}}
\]

### 问题 2：量化后，Bytes 减少了多少？

如果：

```text
计算量基本不变
FP16 → INT4
Bytes 约减少到 1/4
```

那么：

\[
AI
=
\frac{\text{Operations}}
{\text{Bytes}}
\]

会明显提高。

如果当前本来就是 Memory Bound，那么这种优化通常特别有效。

---

## 12A.13 三个典型 LLM 场景

| 场景 | 数据复用情况 | 典型倾向 |
|---|---|---|
| Batch=1 Decode | 权重搬一次，主要服务一个 token | Memory Bound |
| Prefill | 同一权重服务很多 token | 更靠近 Compute Bound |
| 大 Batch GEMM | 权重复用率更高 | 更容易 Compute Bound |

实际情况仍会受到：

- GPU 型号
- Batch Size
- Sequence Length
- 数据类型
- Kernel 实现
- Cache 命中率
- Tensor Core 利用率

等因素影响。

---

## 12A.14 一句话理解计算密度

最通俗的理解：

\[
\boxed{
\text{计算密度}
=
\text{每搬一份数据，我到底榨出了多少次计算}
}
\]

如果：

```text
搬很多
算很少
```

就是：

\[
AI低
\Rightarrow
Memory\ Bound
\]

如果：

```text
搬一次
反复算很多次
```

就是：

\[
AI高
\Rightarrow
更可能 Compute\ Bound
\]

这也是判断“量化到底应该主要优化搬运，还是主要优化计算”的核心依据。


# 13. 量化为什么能减少数据搬运时间

假设 7B 模型。

FP16：

\[
2Byte/parameter
\]

理论权重大小：

\[
7B\times2Byte
\approx14GB
\]

INT4：

\[
0.5Byte/parameter
\]

理论：

\[
7B\times0.5Byte
\approx3.5GB
\]

忽略 scale 等额外信息。

所以：

```text
FP16：
需要搬 14GB

INT4：
需要搬约 3.5GB
```

同样显存带宽下：

\[
\boxed{
数据量约减少到 1/4
}
\]

这就是量化最重要的加速来源之一。

---

## 13.1 “有效带宽”提高

物理显存带宽可能还是：

\[
500GB/s
\]

但每个参数从：

\[
2Byte
\]

变成：

\[
0.5Byte
\]

那么相同时间里能送到计算单元附近的参数数量更多。

所以可以理解为：

> **物理带宽没变，但参数级“有效带宽”提高了。**

---

# 14. 量化为什么还可能减少计算时间

量化不只减少搬运。

如果硬件原生支持低精度计算，低 bit 数据还可能提高计算吞吐。

例如 256-bit SIMD Register。

FP32：

\[
256/32=8
\]

能装 8 个。

INT8：

\[
256/8=32
\]

能装 32 个。

所以相同宽度的数据通路里：

```text
FP32：
[8 个]

INT8：
[32 个]
```

如果 CPU 提供对应向量指令，就可能：

> 一条指令处理更多数据。

GPU Tensor Core 也是类似思想。

因此：

\[
\boxed{
量化加速
=
减少数据搬运
+
可能提高低精度计算吞吐
}
\]

---

# 15. “对齐”到底指什么

计算机领域“对齐”有很多含义。

量化性能里常见：

1. 内存对齐
2. SIMD 宽度对齐
3. Tensor Core tile 对齐
4. 量化 block 对齐
5. IEEE 754 指数对齐

它们不是同一件事。

---

## 15.1 内存对齐

例如 SIMD 一次适合处理 32 Byte。

如果数据刚好从适合的边界开始：

```text
|--------32 Byte--------|
```

读取非常规整。

如果跨边界：

```text
前一块 | 数据 | 后一块
```

可能需要多次读取或拼接。

---

## 15.2 SIMD 宽度对齐

假设一次处理 8 个 FP32。

如果维度是：

```text
16
```

可以：

```text
8 + 8
```

非常规整。

如果是：

```text
18
```

则：

```text
8 + 8 + 2
```

最后两个需要特殊处理。

---

## 15.3 Tensor Core Tile 对齐

矩阵计算通常会切成 tile：

```text
┌────┬────┬────┐
│tile│tile│tile│
├────┼────┼────┤
│tile│tile│tile│
└────┴────┴────┘
```

如果矩阵维度可以整齐切分，效率通常更高。

---

## 15.4 量化 Block 对齐

例如量化格式：

```text
32 个 INT4 权重 + 1 个 scale
```

一个 block 一组。

如果维度：

\[
4096/32=128
\]

刚好是 128 个完整 block。

如果是 4100：

```text
128 个完整 block
+
4 个尾部元素
```

尾部就可能需要特殊处理。

---

# 16. IEEE 754 中的指数对齐

这是另一种完全不同的“对齐”。

浮点加减法前，需要把指数变成一致。

例如：

\[
1.101\times2^3
\]

和：

\[
1.010\times2^1
\]

不能直接尾数相加。

要先把第二个数调整：

\[
1.010\times2^1
=
0.01010\times2^3
\]

然后：

\[
1.10100\times2^3
+
0.01010\times2^3
\]

再做尾数加法。

这叫：

\[
\boxed{Exponent\ Alignment}
\]

即：

> 指数对齐 / 阶码对齐。

---

## 16.1 为什么小数可能“加不上去”

如果两个浮点数指数差很大，小数的尾数会不断右移。

例如：

\[
100000000 + 1
\]

小数的有效位可能在对齐过程中被移出可表示范围。

于是可能出现：

\[
100000000+1
\approx
100000000
\]

这也是浮点误差的重要来源。

---

# 17. FP16 和 FP32 能不能一起计算

可以。

但不是把两个原始 bit 格式直接硬凑在一起。

通常会先确定统一计算格式。

例如：

\[
FP16 + FP32
\]

可能先：

\[
FP16\rightarrow FP32
\]

然后：

\[
FP32+FP32
\]

之后才进行：

```text
指数比较
↓
指数对齐
↓
尾数相加
↓
规格化
↓
舍入
```

所以要区分：

> **类型统一** 和 **指数对齐** 是两件不同的事情。

---

# 18. 为什么不同算子可以使用不同精度

现代模型计算图不一定统一用一种精度。

例如：

```text
Linear / GEMM
可能低精度

Softmax
可能提高部分计算精度

RMSNorm / LayerNorm
部分 reduction 可能使用高精度

输出
再转回 FP16 / BF16
```

这就是：

\[
\boxed{Mixed\ Precision}
\]

混合精度计算。

---

# 19. Storage、Compute、Accumulator、Output 精度

这是本章最重要的概念之一：

\[
\boxed{
Storage\ dtype
\neq
Compute\ dtype
\neq
Accumulator\ dtype
\neq
Output\ dtype
}
\]

例如一个量化 Linear：

```text
Weight Storage: INT4
Activation:     FP16
Multiply:       FP16
Accumulator:    FP32
Output:         FP16
```

所以：

> “INT4 模型”并不意味着整个模型从头到尾全部执行 INT4 运算。

---

## 19.1 一个典型流程

```text
INT4 Weight
    ↓
VRAM 中以 INT4 存储和搬运
    ↓
进入 kernel
    ↓
unpack / dequant
    ↓
FP16
    ↓
FP16 × FP16
    ↓
FP32 accumulate
    ↓
输出 FP16
```

可以记成：

\[
INT4_{storage}
\rightarrow
FP16_{multiply}
\rightarrow
FP32_{accumulate}
\rightarrow
FP16_{output}
\]

---

# 20. INT8 × INT8 → INT32 accumulate

这是理解低精度硬件计算最简单的例子。

假设：

\[
a=5,\qquad b=3
\]

INT8：

```text
a = 00000101
b = 00000011
```

二进制乘法：

```text
      00000101
×     00000011
----------------
      00000101
     00000101
----------------
      00001111
```

即：

\[
00001111_2=15
\]

---

## 20.1 为什么要更宽的结果

INT8 范围：

\[
[-128,127]
\]

但：

\[
127\times127=16129
\]

显然已经放不进 INT8。

所以低精度输入的乘法结果需要更宽的数据通路。

例如：

```text
INT8 × INT8
      ↓
更宽的乘积
      ↓
INT32 accumulator
```

---

## 20.2 累加例子

计算：

\[
5\times3+7\times4
\]

第一项：

\[
5\times3=15
\]

INT32：

```text
00000000 00000000 00000000 00001111
```

第二项：

\[
7\times4=28
\]

INT32：

```text
00000000 00000000 00000000 00011100
```

相加：

```text
  00000000 00000000 00000000 00001111
+ 00000000 00000000 00000000 00011100
------------------------------------------------
  00000000 00000000 00000000 00101011
```

得到：

\[
43
\]

所以：

\[
\boxed{
INT8\times INT8\rightarrow INT32\ accumulate
}
\]

其中“更高精度”主要意味着：

> 使用更多 bit，避免乘法和累加溢出。

---

# 21. FP16 × FP16 → FP32 accumulate

假设：

\[
a=1.5
\]

\[
b=1.25
\]

FP16：

- 1 bit sign
- 5 bit exponent
- 10 bit fraction

Bias：

\[
15
\]

---

## 21.1 1.5 的 FP16

\[
1.5=1.1_2\times2^0
\]

所以：

```text
sign = 0
exponent = 0 + 15 = 15 = 01111
fraction = 1000000000
```

编码：

```text
0 | 01111 | 1000000000
```

---

## 21.2 1.25 的 FP16

\[
1.25=1.01_2\times2^0
\]

所以：

```text
0 | 01111 | 0100000000
```

---

## 21.3 浮点乘法步骤

### 符号

\[
0\oplus0=0
\]

结果为正。

### 指数

\[
E=0+0=0
\]

浮点乘法不需要像加法一样先做指数对齐。

### 有效数字相乘

\[
1.1_2\times1.01_2
\]

等于：

\[
1.111_2
\]

也就是：

\[
1.875
\]

结果：

\[
1.111\times2^0
\]

---

## 21.4 进入 FP32 accumulator

FP32：

- 1 bit sign
- 8 bit exponent
- 23 bit fraction

Bias：

\[
127
\]

1.875：

\[
1.111\times2^0
\]

因此：

```text
0 | 01111111 | 11100000000000000000000
```

注意：

> 数值没有变，还是 1.875。

只是放进了更宽的表示里。

---

## 21.5 为什么累加用 FP32

假设：

\[
ACC=10.0
\]

执行：

\[
ACC=10.0+1.875
\]

如果 accumulator 是 FP32，就可以用 FP32 的：

- 更宽 exponent
- 更多 fraction bits

进行后续累加。

这可以显著降低连续累加过程中的舍入误差。

---

## 21.6 需要特别注意

通常写：

\[
FP16\times FP16\rightarrow FP32
\]

是为了方便理解。

不要死记成：

```text
先严格产生一个 FP16 结果
↓
再软件转换成 FP32
```

更准确的描述是：

> 硬件读取 FP16 输入，在内部完成低精度乘法，并把乘积贡献累加到 FP32 accumulator。

---

# 22. 量化、混合精度、Kernel、硬件之间是什么关系

可以分成四层：

```text
① 数值表示
FP32 / FP16 / FP8 / INT8 / INT4

        ↓

② 量化算法
决定如何从高精度压成低精度
scale / zero point / block 等

        ↓

③ 推理 Kernel
决定数据怎么 unpack、dequant、multiply、accumulate

        ↓

④ CPU / GPU 硬件
决定原生支持哪些数据类型和指令
```

例如同一个 Q4 模型：

```text
x86 + AVX2
Apple ARM + NEON
NVIDIA CUDA
```

可能走完全不同的执行路径。

所以：

> **同一个量化模型，在不同硬件和不同框架中，底层计算方式可能完全不同。**

---

## 22.1 Mixed Precision 不等于 Quantization

例如：

\[
FP16\times FP16\rightarrow FP32\ accumulate
\]

属于：

\[
\boxed{Mixed\ Precision\ Execution}
\]

即使没有 INT4 / INT8 量化，也可以使用。

而：

```text
FP16 Weight
↓
INT4 Weight
```

则属于量化。

两者经常一起出现，但不是同一个概念。

# 23. 量化到底影响计算机中的哪些硬件

| 硬件/层级 | 量化可能带来的影响 |
|---|---|
| SSD | 模型文件更小，加载更快 |
| RAM | 内存占用更少 |
| CPU RAM 带宽 | 单位时间可以搬更多参数 |
| PCIe | CPU ↔ GPU 传输量减少 |
| VRAM | 显存占用降低 |
| 显存带宽 | 同样时间内可以读取更多参数 |
| Cache | 相同容量能缓存更多权重 |
| Register | 固定位宽下能装更多低精度元素 |
| CPU SIMD | 一条指令可能处理更多低精度数据 |
| GPU Tensor Core | 某些低精度矩阵计算吞吐更高 |
| Kernel | 可以融合 unpack、dequant、GEMM |

因此：

\[
\boxed{
量化改变的是整个 Memory + Compute Pipeline
}
\]

而不是只影响“模型文件大小”。

# 24. 为什么 bit 越低不一定越快

不能简单认为：

```text
INT2 > INT3 > INT4 > INT8 > FP16
```

在速度上一定成立。

因为真实时间是：

\[
T=
T_{load}
+
T_{unpack}
+
T_{dequant}
+
T_{compute}
+
T_{other}
\]

低 bit 虽然：

```text
数据更小
```

但也可能带来：

- unpack 更复杂
- bit shift / mask 更多
- scale 处理更多
- 硬件没有原生支持
- 内存布局不规则
- block 不对齐
- kernel 优化不成熟

例如 INT3：

```text
3 bit
```

不像 INT4：

```text
4 + 4 = 8 bit
```

可以刚好两个数装一个 Byte。

INT3 在 bit packing 上可能更麻烦。

所以：

> **低 bit 是否更快，最终取决于量化格式、Kernel、硬件支持和数据布局，而不只是 bit 数。**

# 24A. TFLOPS 是什么：衡量“每秒能算多少”

TFLOPS 一般读作 **Tera FLOPS**。

其中：

- FLOP = Floating Point Operation，一次浮点运算
- FLOPS = Floating Point Operations Per Second，每秒浮点运算次数
- Tera = $10^{12}$

因此：

$$
\boxed{1\text{ TFLOPS}=10^{12}\text{ FLOPS}}
$$

即：每秒 1 万亿次浮点运算。

例如某 GPU 的 FP32 峰值算力为：

$$
40\text{ TFLOPS}
$$

表示理论上每秒最多可以执行：

$$
40\times10^{12}
$$

次 FP32 浮点运算。

需要和内存带宽区分：

$$
\text{TFLOPS}\rightarrow\text{每秒能算多少}
$$

$$
\text{GB/s}\rightarrow\text{每秒能搬多少数据}
$$

因此 Roofline Model 本质上就是在比较：**硬件算得有多快，和内存给数据给得有多快。**

# 24B. 未量化和量化后，精度到底差在哪里

考虑一个简单线性层：

$$
y=xW
$$

其中：

$$
x=\begin{bmatrix}1.2 & -0.7\end{bmatrix}
$$

$$
W=\begin{bmatrix}0.82 & -1.37\\2.26 & 0.54\end{bmatrix}
$$

## 24B.1 未量化 FP32 计算

$$
y_1=1.2\times0.82+(-0.7)\times2.26=-0.598
$$

$$
y_2=1.2\times(-1.37)+(-0.7)\times0.54=-2.022
$$

因此：

$$
\boxed{y_{\text{FP32}}=[-0.598,-2.022]}
$$

## 24B.2 量化权重

为了方便手算，假设：

$$
scale=0.1
$$

量化公式：

$$
q=\operatorname{round}\left(\frac{w}{scale}\right)
$$

反量化：

$$
\hat w=q\times scale
$$

于是：

- $0.82\rightarrow0.8$
- $-1.37\rightarrow-1.4$
- $2.26\rightarrow2.3$
- $0.54\rightarrow0.5$

得到：

$$
\hat W=\begin{bmatrix}0.8 & -1.4\\2.3 & 0.5\end{bmatrix}
$$

这里已经发生：

$$
\boxed{\text{Quantization Error}}
$$

也就是原始连续高精度值，被映射到了有限的离散值集合。

## 24B.3 使用量化权重计算

$$
\hat y_1=1.2\times0.8+(-0.7)\times2.3=-0.65
$$

$$
\hat y_2=1.2\times(-1.4)+(-0.7)\times0.5=-2.03
$$

因此：

$$
\boxed{y_{\text{quant}}=[-0.65,-2.03]}
$$

| 输出 | FP32 | 量化后 | 绝对误差 |
|---|---:|---:|---:|
| $y_1$ | -0.598 | -0.650 | 0.052 |
| $y_2$ | -2.022 | -2.030 | 0.008 |

如果：

$$
\hat W=W+E
$$

其中 $E$ 是量化误差，那么：

$$
\hat y=x\hat W=x(W+E)=xW+xE
$$

所以：

$$
\boxed{\hat y=xW+xE}
$$

其中 $xE$ 就是量化误差传播到输出后的结果。

# 24C. 量化误差和计算误差不是一回事

可以把总误差粗略理解为：

$$
\boxed{\text{Total Error}\approx\text{Quantization Error}+\text{Computation Error}+\text{Output Rounding Error}}
$$

## 24C.1 量化误差

发生在：

$$
FP32/FP16\rightarrow INT8/INT4/FP8
$$

例如：

$$
0.8237\rightarrow0.82
$$

这部分信息一旦丢失，后面即使使用 FP32 计算，也无法恢复原始的 $0.8237$。

## 24C.2 计算误差

发生在乘法、加法、连续累加、舍入、reduction 等过程中。

因此硬件常采用：

$$
\boxed{\text{低精度输入}+\text{高精度累加}}
$$

例如：

$$
FP16\times FP16\rightarrow FP32\ accumulate
$$

或：

$$
INT8\times INT8\rightarrow INT32\ accumulate
$$

核心目的不是修复量化误差，而是：**避免在已经接受低精度输入之后，计算过程中继续产生过多新误差。**

# 24D. 为什么 FP16 连续累加容易丢精度

根本原因是 IEEE 754 中的：

$$
\boxed{\text{指数对齐}+\text{有效位有限}+\text{舍入}}
$$

FP16 的 fraction 为 10 bit，加上隐藏位 $1$，实际有效精度约为 11 bit。

考虑：

$$
2048+0.5
$$

其中：

$$
2048=1.0\times2^{11}
$$

而：

$$
0.5=1.0\times2^{-1}
$$

指数差：

$$
11-(-1)=12
$$

浮点加法必须先指数对齐：

$$
0.5=0.000000000001\times2^{11}
$$

此时有效的 $1$ 已被右移到非常靠后的位，而 FP16 能保留的有效位有限，于是该低位可能被舍掉。

最终：

$$
\boxed{2048+0.5\approx2048}
$$

而不是 $2048.5$。

## 24D.1 为什么数值越大，能分辨的最小间隔越大

FP16 在 $1$ 附近，相邻可表示数间隔大约是：

$$
2^{-10}\approx0.0009766
$$

但在：

$$
2048=2^{11}
$$

附近，间隔约为：

$$
2^{11-10}=2
$$

因此 FP16 在这一段更接近：

```text
2046
2048
2050
2052
...
```

所以 $2048+0.5$ 无法形成一个新的可表示 FP16 值。

## 24D.2 为什么 FP32 accumulator 更稳定

FP32 fraction 有 23 bit。

在 $2048=2^{11}$ 附近，相邻数间隔约为：

$$
2^{11-23}=2^{-12}=0.000244140625
$$

因此 $2048+0.5$ 对 FP32 来说完全可以区分。

这就是：

$$
\boxed{FP16\times FP16\rightarrow FP32\ accumulate}
$$

非常常见的原因。

# 24E. 算子、Kernel、硬件计算单元之间的关系

这三个概念必须分层理解。

## 24E.1 算子：我要算什么

例如：

```python
y = x @ W
```

对应：

$$
\boxed{\text{Matrix Multiply / GEMM Operator}}
$$

常见算子包括：Linear、Softmax、RMSNorm、RoPE、Attention、Dequant。它们属于软件层定义的计算任务。

## 24E.2 Kernel：在某个硬件上具体怎么实现

同一个 GEMM 算子，可以有：

```text
FP32 GEMM kernel
FP16 Tensor Core GEMM kernel
INT8 GEMM kernel
INT4 Quantized GEMM kernel
```

数学任务都类似：

$$
Y=XW
$$

但具体怎么加载数据、怎么分块、怎么 unpack、使用什么指令、如何累加，都可能不同。

所以：

$$
\boxed{\text{Operator}\rightarrow\text{Kernel}\rightarrow\text{Hardware}}
$$

## 24E.3 硬件计算单元：真正执行物理计算

CPU 常见：ALU、FPU、SIMD Unit。

GPU 常见：CUDA Core、Tensor Core。

这些硬件单元最终执行 multiply、add、FMA、dot product 等底层运算。

## 24E.4 Attention 的例子

$$
Attention(Q,K,V)=Softmax\left(\frac{QK^T}{\sqrt d}\right)V
$$

可以粗略拆成：

```text
QKᵀ
↓
GEMM
↓
Tensor Core

Softmax
↓
exp / add / divide
↓
CUDA Core

Softmax(...) × V
↓
GEMM
↓
Tensor Core
```

所以一个算子不一定只对应一种硬件计算单元。

# 24F. 量化中的算子优化，大致在优化什么

量化算子优化的核心可以概括为：

$$
\boxed{\text{少搬}+\text{少解}+\text{少转}+\text{多并行}+\text{多复用}}
$$

## 24F.1 少搬：减少 Memory Traffic

较差实现：

```text
INT4 权重
↓
全部反量化成 FP16
↓
写回 VRAM
↓
再读取 FP16
↓
FP16 GEMM
```

更好的实现：

```text
INT4 权重
↓
边读取边 unpack
↓
边 dequant
↓
直接参与 GEMM
```

核心是减少中间结果反复写回显存。

## 24F.2 Kernel Fusion

把：

```text
dequant
+
GEMM
```

融合到同一个 kernel，甚至进一步融合 bias、activation，尽量少经过 VRAM 中间写回。

## 24F.3 少解：减少 INT4 unpack 开销

INT4 常把两个值打包进一个 Byte：

```text
xxxx yyyy
```

计算前需要：

```text
load
↓
mask
↓
shift
↓
unpack
↓
convert
```

优秀 kernel 会让这些步骤 SIMD 化或 warp 并行化。

## 24F.4 少转：减少中间类型转换

尽量避免无意义的：

```text
INT4
↓
INT8
↓
FP16
↓
FP32
```

如果硬件支持更直接路径，应优先利用 INT8 dot product、INT8 Tensor Core、FP8 Tensor Core 等专用低精度能力。

## 24F.5 多并行

CPU 侧常见 AVX2、AVX-512、NEON；GPU 侧常见 warp、CUDA Core、Tensor Core。低精度格式可以让固定宽度的数据通路一次处理更多元素。

## 24F.6 多复用：提高 Arithmetic Intensity

把数据从 RAM / VRAM 搬进 Cache、Shared Memory、Register 后尽量重复利用。

如果：

$$
AI=\frac{\text{Operations}}{\text{Bytes Moved}}
$$

那么在搬运量基本不变时增加复用次数，就会让：

$$
AI\uparrow
$$

## 24F.7 Tiling / Blocking

大矩阵例如：

$$
4096\times4096
$$

通常会切成多个 Tile：

```text
Tile 0
Tile 1
Tile 2
...
```

每个 Tile 尽量走：

```text
VRAM
↓
Shared Memory / Cache
↓
Register
↓
反复计算
```

目的是提高数据局部性、Cache 命中率、Shared Memory 复用率和 Register 复用率。

## 24F.8 Block Size 与硬件对齐

例如：

```text
32 个 INT4 权重
+
1 个 scale
```

如果 block size、SIMD width、Tensor Core tile、memory load width 匹配较好，就能减少尾部处理、mask、scalar fallback 和多余 shuffle。

## 24F.9 Scale / Zero Point 优化

量化常见：

$$
w\approx s(q-z)
$$

常见优化包括：多个权重共享一个 scale、scale 尽量驻留 Register、一个 block 批量处理、dequant 和 MAC 融合。

# 24G. 看一个量化 Kernel 时，应该问哪些问题

以后分析 llama.cpp、CUDA、Triton 或其他量化 kernel，可以优先检查：

1. 权重以什么精度存储？
2. 从哪一级内存读取？
3. 什么时候 unpack？
4. 什么时候 dequant？
5. scale / zero point 放在哪里？
6. 中间结果是否写回 RAM / VRAM？
7. 一个 block 一次处理多少权重？
8. 是否使用 SIMD / warp / Tensor Core？
9. 一个 Tile 的数据被复用了多少次？
10. accumulator 是什么精度？
11. 是否存在 Kernel Fusion？
12. 当前算子是 Memory Bound 还是 Compute Bound？

如果这几个问题都能回答，就已经可以比较系统地分析一个量化算子的实现质量。

# 26. 最后需要牢牢记住的结论

## 结论 1：大模型推理不只是“算”

\[
\boxed{
Inference
=
Memory\ Movement
+
Compute
}
\]

---

## 结论 2：很多 LLM Decode 场景是 Memory Bound

因为：

```text
每生成一个 token
↓
需要访问大量权重
↓
但只服务一个 token
```

所以权重量化特别有价值。

---

## 结论 3：量化有两类加速

### Memory-side

```text
FP16 → INT4
↓
权重更小
↓
RAM/VRAM/Cache 搬运更少
↓
带宽压力下降
```

### Compute-side

```text
低精度
↓
SIMD / Tensor Core 一次可能处理更多数据
↓
低精度 MAC 吞吐提高
```

---

## 结论 4：不同阶段可以使用不同精度

\[
\boxed{
Storage
\neq
Compute
\neq
Accumulator
\neq
Output
}
\]

例如：

```text
Weight Storage : INT4
Multiply       : FP16
Accumulator    : FP32
Output         : FP16
```

---

## 结论 5：低精度输入 + 高精度累加非常常见

整数：

\[
INT8\times INT8\rightarrow INT32\ accumulate
\]

浮点：

\[
FP16\times FP16\rightarrow FP32\ accumulate
\]

核心思想：

> **低精度负责节省存储、带宽和提高吞吐；高精度 accumulator 负责避免溢出和降低累计误差。**

---

## 结论 6：“量化模型”不等于“全程低精度计算”

例如 Q4 模型完全可能：

```text
INT4 Weight
↓
搬运
↓
unpack / dequant
↓
FP16 multiply
↓
FP32 accumulate
↓
FP16 output
```

因此以后分析一个量化方案时，应该问四个问题：

1. 权重是什么精度存储？
2. Activation 是什么精度？
3. 真正乘法使用什么精度？
4. Accumulator 使用什么精度？

如果这四个问题都能回答清楚，就已经开始真正理解一个量化推理系统了。

---


## 结论 7：先看计算密度，再判断量化应该优化哪一侧

判断一个算子的性能瓶颈，可以结合：

\[
AI=\frac{\text{Operations}}{\text{Bytes Moved}}
\]

以及：

\[
P_{\text{actual}}
\approx
\min
\left(
P_{\text{peak}},
BW\times AI
\right)
\]

如果：

\[
AI
\]

较低，更容易是：

\[
\boxed{\text{Memory Bound}}
\]

此时量化最重要的价值通常是：

\[
\boxed{\text{减少数据搬运量}}
\]

如果：

\[
AI
\]

较高，更容易进入：

\[
\boxed{\text{Compute Bound}}
\]

此时更应该关注：

\[
\boxed{\text{低精度硬件计算吞吐是否真正提高}}
\]




## 结论 8：量化误差和计算误差必须分开理解

量化误差发生在高精度表示到低精度离散表示的映射阶段；高精度 accumulator 主要减少的是计算过程中的舍入和累加误差，不能恢复已经丢失的量化信息。

## 结论 9：算子、Kernel、硬件是三个层级

$$
\boxed{\text{算子}\rightarrow\text{Kernel}\rightarrow\text{硬件计算单元}}
$$

其中算子决定“算什么”，Kernel 决定“在这块硬件上具体怎么算”，CPU/GPU 计算单元真正执行物理运算。

## 结论 10：量化算子优化的五个核心词

$$
\boxed{\text{少搬}+\text{少解}+\text{少转}+\text{多并行}+\text{多复用}}
$$

本质上是在同时优化 Memory Traffic 和 Compute Throughput。


# 27. 一句话总复盘

> **大模型推理的底层，本质上是把权重和 activation 从 RAM/VRAM 逐层搬到 Cache 和 Register，再由 CPU SIMD、CUDA Core 或 Tensor Core 执行大量乘加。量化一方面让沿途搬运的数据更少、Cache 利用率更高，另一方面在硬件支持时可以让低精度计算单元一次处理更多数据；与此同时，实际推理通常采用混合精度，因此权重的存储精度、乘法精度、累加精度和输出精度可以完全不同。**
