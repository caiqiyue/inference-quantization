# 大模型推理芯片基础入门笔记

> 适合背景：软件 / 大模型方向为主，但对芯片、硬件、体系结构了解较少。  
> 目标：先建立一套统一的“芯片执行心智模型”，听懂公司里常见的 PCIe、TE、VE、CE、寄存器、计数器、信号量、时钟频率、CModel、FPGA、ASIC 等术语。

---

## 1. 先建立整体心智模型

可以先把一颗大模型推理芯片理解成：

```text
                 Host / CPU
                     │
                     │ PCIe
                     ▼
┌─────────────────────────────────┐
│          AI 推理芯片             │
│                                 │
│    HBM / DDR / Device Memory    │
│              │                  │
│        ┌─────▼─────┐            │
│        │ 片上 SRAM │            │
│        └─────┬─────┘            │
│              │                  │
│    ┌─────────┼────────────┐     │
│    ▼         ▼            ▼     │
│   TE        VE           CE     │
│ 矩阵计算   向量计算     搬运/控制 │
│    │         │            │     │
│    └─────────┼────────────┘     │
│              │                  │
│   Register / Counter /          │
│   Semaphore / Signal            │
└─────────────────────────────────┘
```

很多看起来毫无关系的名词，其实都在描述同一件事：

> **数据如何进入芯片、如何被搬运、如何被计算、各模块如何同步，以及软件如何控制这些硬件。**

---

# 2. PCIe：CPU 和推理芯片之间的高速通道

PCIe 可以先理解为：

> **服务器 CPU 和 AI 推理卡之间的高速公路。**

例如：

```text
CPU
 │
 │ PCIe
 ▼
AI 推理芯片
```

CPU 可能通过 PCIe 传：

- 模型权重
- 输入 Tensor
- Command / 指令
- 内存地址
- 计算结果

一个简化流程：

```text
Python / C++
    ↓
Runtime / Driver
    ↓
CPU
    ↓
PCIe
    ↓
推理芯片
    ↓
执行计算
```

### 2.1 为什么 PCIe 性能重要

如果芯片内部算得非常快，但 CPU 往芯片送数据很慢：

```text
CPU =====较慢=====→ Chip
```

那么芯片可能出现：

```text
算一会
↓
等数据
↓
再算一会
↓
再等数据
```

所以以后听到：

```text
PCIe bandwidth 不够
```

可以理解为：

> CPU 和芯片之间的数据通路成为瓶颈。

# 3. TE、VE、CE：芯片中的不同 Engine

注意：

> TE、VE、CE 并不是所有公司完全统一的缩写。

不同公司的定义可能不同，必须以公司内部架构文档为准。

不过在 AI 推理芯片中，常见理解如下。

---

## 3.1 TE：Tensor Engine / Tensor Execution Engine

TE 通常负责：

> **矩阵、张量类重计算任务。**

例如大模型最常见的：

\[
Y = XW
\]

如：

```text
[1 × 1024]
    ×
[1024 × 4096]
    ↓
[1 × 4096]
```

这种 GEMM / GEMV / Dot Product 通常非常适合由 TE 完成。

可以把 TE 理解成：

> **专门负责大量乘加运算的“大力士”。**

例如量化推理中可能出现：

```text
NVFP4 Weight
     ×
Activation
     ↓
    TE
     ↓
高精度 Accumulate
```

以后看到：

- TE busy
- TE utilization
- TE stall
- TE counter

本质上都在关注：

> **矩阵计算单元到底有没有在正常工作、忙了多久、是否在等待。**

---

## 3.2 VE：Vector Engine

VE 通常负责：

> **向量计算、逐元素运算，以及不适合矩阵单元处理的操作。**

例如：

```text
RMSNorm
Softmax
SiLU
RoPE
Add
Mul
Scale
element-wise op
```

一个简化理解：

```text
TE → 擅长矩阵
VE → 擅长向量 / element-wise
```

例如 Transformer 中可能出现：

```text
RMSNorm      → VE
Linear       → TE
RoPE         → VE
QK MatMul    → TE
Softmax      → VE
AV MatMul    → TE
```

具体仍需以实际芯片架构为准。

---

## 3.3 CE：含义需要结合公司内部定义

CE 是最容易歧义的一个缩写。

常见可能有：

### Copy Engine

主要负责数据搬运：

```text
HBM → SRAM
SRAM → HBM
Host → Device
```

### Compute Engine

某种计算执行单元。

### Command Engine

负责：

- 接收 command
- 解析 command
- 调度其他 Engine
- 控制执行流程

所以遇到 CE，最合理的做法是先确认：

> “这个 CE 是 Copy Engine、Compute Engine，还是 Command Engine？”

---

# 4. 为什么“搬数据”非常重要

大模型推理不是只有计算。

例如：

\[
Y = XW
\]

权重 W 如果在 HBM 中，通常需要经历：

```text
HBM
 │
 │ 搬运
 ▼
SRAM
 │
 │ 送入计算单元
 ▼
TE
 │
 ▼
计算
```

所以实际执行常常是：

```text
搬数据
↓
计算
↓
搬数据
↓
计算
```

这也是为什么推理性能经常不仅取决于算力，还取决于：

- 内存带宽
- 数据复用
- SRAM 容量
- DMA / Copy Engine
- Pipeline

### 4.1 Pipeline 思想

理想情况：

```text
时间 ─────────────────────→

CE: 搬 A | 搬 B | 搬 C | 搬 D
TE:      算 A | 算 B | 算 C | 算 D
```

即：

> **搬下一块数据时，同时计算当前数据。**

这比：

```text
搬 A
算 A
搬 B
算 B
```

效率高很多。

---

# 5. Register：寄存器

可以先把硬件 Register 理解成：

> **芯片内部用于保存配置、状态和控制信息的一小块硬件状态。**

例如一个 Copy Engine 可能有：

```text
SRC_ADDR
DST_ADDR
SIZE
START
STATUS
```

含义分别可能是：

```text
源地址
目标地址
传输大小
开始执行
当前状态
```

例如软件写：

```text
SRC_ADDR = 0x100000
DST_ADDR = 0x200000
SIZE     = 4096
START    = 1
```

意思类似：

> 从 0x100000 搬 4096 Byte 到 0x200000，然后开始执行。

执行完以后：

```text
STATUS = 1
```

软件就知道任务完成了。

所以 Register 是非常重要的：

```text
软件
 ↓
Register
 ↓
硬件
```

控制接口。

---

# 6. 高位和低位

一个 8 bit 数：

```text
10110110
```

可以写成：

```text
bit7 bit6 bit5 bit4 bit3 bit2 bit1 bit0

 1    0    1    1    0    1    1    0
 ↑                                  ↑
高位                                低位
MSB                                 LSB
```

- LSB：Least Significant Bit，最低有效位
- MSB：Most Significant Bit，最高有效位

因为：

\[
bit0 = 2^0
\]

\[
bit1 = 2^1
\]

\[
...
\]

\[
bit7 = 2^7
\]

越高位，对整体数值影响越大。

---

## 6.1 为什么芯片代码经常“取高位 / 低位”

因为一个 32-bit Register 可能同时存很多字段：

```text
31                         16 15                   0
┌────────────────────────────┬─────────────────────┐
│          field A           │       field B       │
└────────────────────────────┴─────────────────────┘
          高 16 位                    低 16 位
```

软件中可能看到：

```c
field_b = reg & 0xFFFF;
field_a = reg >> 16;
```

因此芯片代码里非常常见：

```text
>>
<<
&
|
0xFF
0xFFFF
```

很多时候都是在操作某几个 bit。

# 7. Signal：硬件信号

可以先简单理解：

> **Signal 是硬件中的某个 0 / 1 状态。**

例如：

```text
ready = 0
```

表示：

> 尚未准备好。

而：

```text
ready = 1
```

表示：

> 已经准备好。

芯片中很常见：

```text
ready
valid
done
busy
enable
reset
interrupt
```

---

## 7.1 “拉高”和“拉低”

芯片工程师经常说：

> 把 done 信号拉高。

通常就是：

```text
done:
0 → 1
```

即进入高电平状态。

而：

> 拉低

通常就是：

```text
1 → 0
```

---

# 8. Semaphore：信号量

可以先把 Semaphore 理解成：

> **不同执行模块之间进行同步和通知的机制。**

最直观的理解：

> “我干完了，你现在可以开始了。”

---

## 8.1 CE 和 TE 的例子

假设：

```text
CE → 搬数据
TE → 做矩阵计算
```

数据需要：

```text
HBM
 ↓
CE
 ↓
SRAM
 ↓
TE
```

TE 不能在 CE 还没搬完数据的时候就开始计算。

所以：

```text
CE
↓
搬数据
↓
搬完
↓
设置 semaphore
↓
TE 收到通知
↓
开始计算
```

例如：

```text
semaphore = 0
```

表示：

> 数据还没准备好。

CE 完成后：

```text
semaphore = 1
```

TE 检查：

```text
semaphore == 1
```

然后开始计算。

---

## 8.2 双向同步

还可以是：

```text
CE
↓
把输入搬到 SRAM
↓
signal TE

TE
↓
执行 GEMM
↓
signal CE

CE
↓
把结果搬回 HBM
```

所以 Semaphore 的核心不是“计算”，而是：

> **协调谁先做、谁后做，以及什么时候可以继续。**

---

# 9. Counter：计数器

Counter 可以先理解成：

> **一个不断记录次数或周期数的数字。**

例如：

```text
完成任务 1 → counter = 1
完成任务 2 → counter = 2
完成任务 3 → counter = 3
```

可以用来判断：

```text
64 个 tile 是否全部完成
```

也可以统计：

- TE busy cycle
- memory stall
- instruction 数
- cache miss
- DMA 次数
- kernel 周期数

因此 Counter 是性能分析中的重要工具。

---

# 10. Clock：时钟

数字芯片内部很多逻辑按照统一节拍工作。

这个节拍叫：

> **Clock，时钟。**

可以想象成：

```text
tick      tick      tick      tick
 |         |         |         |
 ▼         ▼         ▼         ▼
cycle 1   cycle 2   cycle 3   cycle 4
```

每一个 tick：

> 一个 Clock Cycle。

---

# 11. Frequency：时钟频率

时钟频率表示：

> **一秒钟有多少个时钟周期。**

例如：

```text
1 GHz
```

意味着：

\[
1GHz = 10^9Hz
\]

即：

> 每秒 10 亿个 cycle。

周期时间：

\[
T = \frac{1}{f}
\]

如果：

\[
f = 1GHz
\]

那么：

\[
T = 1ns
\]

所以：

```text
1 GHz
→ 1 cycle ≈ 1 ns
```

如果：

```text
2 GHz
```

则：

```text
1 cycle ≈ 0.5 ns
```

---

## 11.1 Cycle、Frequency 和延迟

假设某个 Kernel：

```text
执行 2000 cycles
```

芯片频率：

```text
1 GHz
```

一个 cycle：

```text
1 ns
```

则延迟：

\[
2000 \times 1ns = 2000ns = 2\mu s
\]

所以：

```text
cycle 数
+
芯片频率
↓
可以换算执行时间
```

---

## 11.2 频率高不等于一定性能高

假设：

```text
芯片 A：
1 GHz
每 cycle 做 100 次计算

芯片 B：
2 GHz
每 cycle 做 20 次计算
```

理论：

```text
A:
1G × 100
= 100G 次/秒

B:
2G × 20
= 40G 次/秒
```

因此芯片性能通常要综合看：

```text
Frequency
×
每 cycle 完成的工作量
×
计算单元数量
×
实际利用率
```

之后会进一步联系到：

```text
TOPS
TFLOPS
利用率
```

---

# 12. CModel：用软件描述 / 模拟硬件行为

CModel 一般可以理解为：

> **使用 C / C++ 编写的芯片行为参考模型。**

例如真实芯片 TE 规定：

```text
NVFP4 Weight
×
Activation
↓
accumulate
↓
output
```

那么 CModel 可以在 CPU 上用 C++ 模拟这个过程。

例如：

```text
读取 NVFP4
↓
模拟 decode
↓
模拟 scale
↓
模拟乘法
↓
模拟 accumulate
↓
输出结果
```

---

## 12.1 CModel 的作用

CModel 经常作为：

> **Golden Model / Reference Model**

也就是“参考答案”。

例如：

```text
CModel 输出
      vs
RTL / FPGA / 真芯片输出
```

如果一致：

```text
说明硬件实现大概率正确
```

如果不一致，就排查：

```text
rounding
scale
overflow
bit 截断
数据搬运
实现逻辑
```

---

# 13. FPGA：可重新配置的硬件

FPGA 全称：

> Field Programmable Gate Array

中文：

> 现场可编程门阵列。

入门阶段可以先理解成：

> **一种内部数字电路结构可以重新配置的真实硬件。**

普通 CPU / ASIC：

```text
芯片制造完成以后
硬件结构基本固定
```

FPGA：

```text
今天配置成一种电路
明天可以重新配置成另一种电路
```

因此 FPGA 很适合：

> **在真正芯片流片之前做硬件原型验证。**

---

# 14. FPGA 和 CModel 的区别

### CModel

运行在 CPU 上：

```text
C / C++ 软件
↓
模拟芯片行为
```

特点：

- 修改快
- 开发方便
- 适合功能验证
- 适合数值验证

---

### FPGA

是真实硬件：

```text
RTL
↓
综合
↓
FPGA
↓
真实硬件电路运行
```

特点：

- 更接近真实芯片
- 可以验证硬件接口
- 可以验证 Driver
- 可以验证实际执行逻辑
- 修改成本比 CModel 高

---

# 15. ASIC：最终定制芯片

ASIC：

> Application-Specific Integrated Circuit

可以理解为：

> **最终真正流片和量产的定制芯片。**

与 FPGA 对比：

```text
FPGA
= 可重复配置
= 适合原型和验证

ASIC
= 硬件结构固定
= 最终产品
```

ASIC 的优势：

- 性能高
- 功耗低
- 面积更优

缺点：

> 流片后如果硬件设计有严重问题，修改代价非常高。

因此前期必须大量依赖：

```text
CModel
RTL Simulation
FPGA
Verification
```

可以先记：

```text
数学 / 算法
   ↓
Python Reference
   ↓
CModel
   ↓
RTL
   ↓
```

其中：

# 17. 把所有术语串成一次完整执行

假设要运行一个 NVFP4 GEMM：

\[
Y = XW
\]

可能出现：

```text
Host CPU
 │
 │ PCIe
 ▼
AI Chip
 │
 ▼
HBM
 │
 │ CE 搬数据
 ▼
SRAM
 │
 │ Semaphore：READY
 ▼
TE
 │
 │ NVFP4 GEMM
 │
 │ Counter 统计 cycle
 ▼
计算完成
 │
 │ Semaphore：DONE
 ▼
CE
 │
 ▼
HBM
```

整个过程中：

```text
Clock:
tick tick tick tick tick tick ...
```

每个模块随着 cycle 推进。

例如：

```text
cycle 100:
CE 开始搬数据

cycle 300:
CE 搬完
semaphore = READY

cycle 301:
TE 开始执行

cycle 1300:
TE 完成
semaphore = DONE
```

那么 TE 大约执行：

```text
1000 cycles
```

如果：

```text
Clock = 1 GHz
```

则大约：

\[
1000 \times 1ns = 1\mu s
\]

这样：

```text
PCIe
CE
TE
SRAM
Register
Signal
Semaphore
Counter
Clock
Cycle
Frequency
```

就全部连起来了。

# 18. 推荐的硬件学习顺序

对于大模型 / 软件背景进入推理芯片公司，不建议一开始就去啃晶体管和复杂数字电路。

更推荐：

```text
1. PCIe / Host / Device
        ↓
2. HBM / DDR / SRAM / Cache
        ↓
3. DMA / CE 数据搬运
        ↓
4. TE / VE 计算单元
        ↓
5. Register
        ↓
6. Signal / Semaphore / Counter
        ↓
7. Clock / Frequency / Cycle
        ↓
8. Instruction
        ↓
9. Pipeline / Stall
        ↓
10. CModel / Simulator
        ↓
11. RTL / FPGA
        ↓
12. ASIC
```

之后如果工作需要，再补：

```text
Verilog
SystemVerilog
组合逻辑
时序逻辑
触发器
FSM
Clock Domain
```

# 20. 最终核心理解

现阶段不要把这些术语看成十几门独立知识。

它们其实围绕同一个问题：

> **一个大模型算子，如何从软件下发到芯片，数据如何进入芯片、如何被搬运到计算单元、不同模块如何同步、硬件如何按时钟执行，以及在真芯片出来前如何通过 CModel 和 FPGA 做验证。**

当这条主线建立以后，再遇到：

```text
DMA
MMIO
BAR
Doorbell
Ready / Valid
Interrupt
Pipeline
Stall
RTL
Verilog
Bitstream
Emulator
Cycle Model
```

就会容易很多，因为它们都只是继续补全这张图。
